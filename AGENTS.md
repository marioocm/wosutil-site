# AGENTS.md

## Project
Static website for WoS Util (Whiteout Survival utility): a rally countdown and a battle simulator. Open source (MIT), hosted on **Cloudflare Pages** at `wosutil.tech`; the reports API lives at `api.wosutil.tech`. Stack: Astro 7 (static output) + TypeScript 7 + Tailwind CSS v4, Vitest 5. Package manager: pnpm 10; CI uses Node 24.

## Structure
- `astro.config.ts` — static Astro config: fixed `https://wosutil.tech` site URL, sitemap, prefetch, the Tailwind Vite plugin and the dev-only trailing-slash relaxation.
- `src/layouts/` — `BaseLayout.astro` (document shell, SEO/OG, fonts, theme init, optional countdown head script) and `SiteLayout.astro` (static header/footer chrome and the `#app` wrapper).
- `src/components/` — static header/footer, the vanilla-TS countdown widgets, the shared hero visual helper, the shared `Same S1` joiner tooltip and the shared segmented toggle.
- `src/pages/` — `reports.astro`, `countdown.astro`, `simulator.astro`, redirecting `404.astro` and generated `robots.txt`.
- `src-app/` — desktop shell build (Astro `srcDir`): `pages/index.astro` (main shell) and `pages/templates.astro` (standalone Template Creator, opened only by `template-creator`).
- `src/scripts/` — page-scoped browser behavior: countdown island, site chrome, hero/joiner pickers, generation preset, troop power, stats, simulation results and the desktop shell client (`app/`, including the standalone template editor).
- `src/lib/` - shared logic, types and Vitest tests. Key modules: countdown/rally helpers, hero data and stats, bundled generation presets, troop-power and stat math, simulation case builder/formatter, nav/theme, reports API base and the browser wasm engine (`src/lib/engine/`).
- `src/styles/` — Tailwind entry (`global.css`), desktop shell classes (`app.css`) and design tokens (`theme.css`).
- `scripts/package-ui.mjs` — copies the desktop shell build (main page and the standalone `templates/` page) into `dist/ui/` and writes its hashed `manifest.json`.
- `astro.app.config.ts` — desktop shell build (`base: '/'`, output `dist-app/`), separate from the public site build.
- `docs/DESIGN.md` — design system source of truth for layout, color, typography, components and motion. **Read it before touching UI.**
- `public/favicon.svg` - site icon; `public/_redirects` serves `/` as a 302 to `/reports/`, rewrites `/reports/*` to the archive and proxies `/downloads/*` to `api.wosutil.tech`.
- `scripts/deploy-pages.mjs` - production build (site, desktop shell bundle and `dist/ui/` package) and Cloudflare Pages direct upload.
- `.github/workflows/ci.yml` - typecheck, tests and builds on pushes/PRs; deployment is manual with `pnpm deploy:pages`.

## Key quirks
- Static output only (`output: 'static'`, no adapter/SSR), served at the domain root. Internal links are root-absolute (`/reports/`, `/countdown/`, `/simulator/`), so they keep working on report-detail URLs such as `/reports/<id>/`. Cloudflare Pages applies `public/_redirects` before assets: `/` returns a 302 to `/reports/` (no HTML redirect flash) and `/reports/*` rewrites to the archive. `src/pages/404.astro` sends any other unknown path to `/reports/`.
- Site chrome is static Astro markup; behavior is in `src/scripts/site-chrome.ts`. New sections: add a `NAV_ITEMS` entry in `src/lib/nav.ts`, a page using `SiteLayout` with the matching `active` value, and a page script only if interactive.
- Navigation is full-page (no ClientRouter; `prefetch: true`). The countdown island is included only on the countdown page through `BaseLayout`'s `countdown` prop and is not shipped to the simulator.
- The `Share config` action lives in the Rally callers card header on the countdown page (not in the header/nav); it copies the current rally/enemy configuration link.
- `#rally-panel`, `#enemy-panel` and `#rally-queue` have CSS `min-height` reservations in `src/styles/global.css` to keep CLS at 0; update them if those layouts change. `scrollbar-gutter: stable` on `html` prevents horizontal shift.
- Countdown is duration-based (MM:SS). Inputs are disabled while running; Reset restores the configured duration and Clear empties it. It stores `endTime` and recomputes `remainingMs` from `Date.now()` on a 250ms tick, so it is drift-free.
- The reports archive is the default route (`/` 302s to `/reports/`; other unknown paths land on the 404 page and redirect there). The UI labels the two armies **Attacker** and **Defender** (the internal side keys stay `left`/`right`); widget and joiner roles follow those labels. Generation presets are fetched from the engine API (`GET /v1/presets`) on startup and overwrite heroes, troops, stats, T12 levels and buffs on every change. The API serves the raw stat panel plus the max city/pets/Gareth modifiers; `src/lib/stat-buffs.ts` applies `(100 + raw) * (1 + up/100) / (1 + down/100) - 100` when building the engine case, with city, pets and same-stat S4 widgets added in the numerator and the opponent's enemy debuffs plus Gareth in the denominator. The `wosutil:generation-change` event connects the selector with the page widgets. There is no static preset snapshot: if the API is unavailable the picker shows “Generation data unavailable”.
- Joiners only contribute their S1, so `src/lib/joiner-packs.ts` mirrors the engine S1 equivalence classes (`SKILL_CLASSES` in `SKILLS_TABLE.md`) and groups interchangeable heroes. The simulator and archive joiner pickers render one `Same S1` pack card per class (epics first, then legendaries oldest generation first); searching one member expands the pack. The archive picker seeds the whole roster (`HEROES`), so every pack and non-pack joiner (e.g. Bahiti) is available immediately; `/v1/meta` only adds archive-only names. The simulator marks selected slots with `=`, and both simulator slots and report-detail joiner chips open the same floating `Same S1` card (`src/components/joiner-tip.ts`) with the effect and interchangeable heroes on hover or focus; clicking a report-detail chip pins the card until the next click elsewhere. Keep this table in sync when the engine equivalence classes change.
- Archive filters reuse the simulator's picker rows (`src/components/hero-option.ts`) for the hero and joiner dialogs; the generation trigger is a three-column `All gens` + Gen 1..N grid. The mode, result and survivors filters and the per-row side pickers use the shared segmented control (`src/components/segmented-toggle.ts`, also used by the simulator's Optimise Ratio side switch): native radios over a sliding inverted thumb. `mode=rally` requires a joiner on either side, `mode=1v1` requires no joiners, and an absent param means any mode. Hero and joiner filters are repeated `hero`/`joiner` query params, each `name` or `name:side` (`any`/`attacker`/`defender`/`both`), ANDed together; each `joiner` entry matches the whole S1 equivalence class (the API expands it through `hero_skills.SKILL_CLASSES` and the report-name aliases), so filtering Jeronimo also returns rallies with Jessie or Jasser. The UI allows up to 6 heroes and 8 joiners, adds a new empty row while under the cap, shows a per-row side toggle (`both` requires the hero or joiner on both sides) and an X control that removes a selected row. The hero picker also offers `No heroes` (`hero=none`, no main hero on either side); it is exclusive, clearing and hiding the other hero rows and its side toggle. `max_gen` is an upper bound enforced by the reports API against every main hero and joiner (epics and unknown names count as always available), not a "has this hero" match. The tier/FC range filters post `tier_min`, `tier_max`, `fc_min` and `fc_max`; the API compares the report's highest tier and that tier's FC (the values shown on the cards), and `fc_min=0`/`fc_max=0` count an empty furnace as FC0. Both bounds start at Any in `src/components/troop-level-control.ts`, a shared tile + FC hexagon control modeled on the simulator. The hexagon keeps the simulator's inverted fill and shows `Any` when unset; `src/components/fc-hex.ts` is the single source for that badge, shared with the simulator tiles and the archive detail cards. Cards and detail tiles render an empty furnace as `FC0`. Detail troop tiles show the count-weighted average tier (truncated to one decimal, e.g. `T11.3`) and FC (truncated to an integer, e.g. `FC9`), matching the game's troop panel; list cards and the detail kicker keep the maximum. The result filter is a four-option `Any`/`Attacker`/`Defender`/`Draw` toggle and the survivors toggle directly below it (`max_survivors`) keeps fights where the surviving army ends under 50%, 25% or 10% of its own troops (one side is always wiped, so that is also the battle's survivor total). A result with zero reports in `/v1/meta` resets the result toggle to `Any`; `No wipe` is not offered. The applied filters are written to `sessionStorage` (`wosutil:report-filters`) and restored when the archive loads without filter params, so leaving for the simulator or another section and coming back keeps them; report-detail history entries also carry the query, and Clear removes the stored value. The reports API image must copy `src/wosutil_sim/hero_stats.py` and `src/wosutil_sim/hero_skills.py` because the generation map and the joiner classes come from `HERO_STATS` and `SKILL_CLASSES` (`deploy/Dockerfile.reports` in `wosutil-sim`). The pickers are seeded from the local roster and joiner packs at init, so they open immediately; `/v1/meta` only merges archive-only names, result availability and the header count, and never gates a control. `/v1/reports` pages are cached in memory for 60s (40 queries) and rendered stale-while-revalidate with an `AbortController`, so a filter change keeps the previous cards visible while the new page loads instead of blanking the grid.
- Report-detail actions sit above the cards, outside them: primary inverted `Simulate`, outlined `Copy link` and outlined `Download JSON` (no CSV). `Simulate` opens `simulator/?battle=<report id>`; `src/scripts/simulator-battle.ts` fetches the public report, `src/lib/report-battle.ts` flattens it into heroes, joiners, troops, T12 levels and the final stat panel, and dispatches `wosutil:simulator-load` (`src/lib/simulator-load.ts`) to the simulator widgets. Because archive stats are already final, the loader resets City/Pets/Gareth to Off and inverts the S4-widget bucket before storing the raw panel, so the engine receives the report's stats unchanged. Mixed troop groups are kept as separate `{tier, fc, count}` groups per class, largest first; Troop Power aligns them into one row per group index and sends each class as an array (single-group classes still use that array shape).
- Hero changes fire `wosutil:hero-change`; with “Sync hero stats” enabled (default) `src/scripts/stat-bonuses.ts` adds the old/new hero expedition-stat difference to that class's raw panel. The Stats Bonuses table shows the effective panel (raw + heroes + city/pets/Gareth + the side's current S4 widgets); raw values live in `data-raw-value`, so buff or widget changes rebuild the visible panel and manual edits invert the transform. The Buffs section toggles City (0/10/20), Pets (max) and Gareth (0-5%) per side, and a change on one side updates both sides because enemy debuffs affect the opponent.
- The reports archive uses the API base (`src/lib/reports.ts`); override it with `PUBLIC_REPORTS_API` at build time. The simulator itself is client-side: `src/lib/engine/worker.ts` loads the Rust wasm built from `wosutil-sim`, and `simulate.ts` sends 4096 seeds to it; each run sends a fresh `seed_base` so repeat clicks resample the battle. Hero skill levels are fixed at 5 in `src/lib/simulation.ts`; T12 levels come from the preset/Troop Power. Battle Details uses `skills[].source_kind` to show the game dash for base/buff skills without a kill counter and a numeric `0` for a kill-counter skill that killed nothing; an older API without the field falls back to a dash for zero and shows only nonzero kills.
- Optimise Ratio runs the same case in the wasm worker (`side: att|def`, 10% coarse grid, 512 final seeds) with a fresh `seed_base` per run. The Rust implementation (`rust/wos_sim_engine/src/api.rs` in `wosutil-sim`) screens the coarse grid at 96 seeds, refines the best centers at 1% with 16 seeds, re-ranks the shortlist at 192 seeds and only then spends the final 512; screening and final stages use disjoint seed streams so the reported win rate is not inflated by selection. Both actions use the shared `createLoadingController` (`src/lib/loading-state.ts`) for a spinner, live elapsed seconds and an indeterminate progress bar; each request is one blocking worker call, so the bar deliberately does not fake a percentage. `buildOptimizeCase` keeps zero-count classes and groups so their tier/FC can receive troops; clicking a result distributes each class total across its troop rows in proportion to their current counts (evenly when every row is empty). Its results reveal with the same 220ms height motion as the Simulation card and show seeds / elapsed_ms plus a Ratio / Win % / Margin table.
- Generation presets are bundled from `src/data/generation-presets.json`; refresh with `reports/loopcal/export_site_presets.py` in `wosutil-sim` when a new generation is published. There is no simulator rate limit; the client computes locally.
- Hero portraits are hotlinked from the Whiteout Survival Wiki (`src/lib/hero-images.ts`); no game art is stored in this MIT-licensed repository. `src/lib/heroes.ts` owns the combat roster. `getHeroImage()` requests the source bucket's `-150x150` rendition (24-52px avatars render at 2x) instead of the 30-210 KB originals. Cloudflare Pages compresses and caches the static assets; Astro fingerprints `/_astro/`.
- Tailwind v4 is CSS-first (`@theme` in `src/styles/theme.css`, no `tailwind.config.js`). Named spacing tokens collide with size utilities: `max-w-md` resolves to 12px, so use arbitrary values (e.g. `max-w-[34rem]`).
- Fonts are self-hosted Fontsource files with custom `@font-face` in `BaseLayout.astro` (`font-display: swap`; both latin subsets — Instrument Sans and Geist Mono — are preloaded so dev and production render the same fonts instead of falling back to system faces with different metrics). Do not add Google Fonts, proprietary fonts or copied Suisse Int'l (commercial license).
- `pnpm typecheck` is `tsc --noEmit`, not `astro check`: Astro 7's checker currently refuses TypeScript 7. Keep `.astro` templates thin and let `pnpm build` validate them.
- The desktop shell (`src-app/pages/index.astro`) is built with `astro.app.config.ts` (`srcDir: 'src-app'`, base `/`, output `dist-app/`) because WosUtil serves it from its own local root. `scripts/package-ui.mjs` copies it to `dist/ui/` with a hashed `manifest.json`; that folder is published at `/ui/` and is the versioned UI artifact consumed by the WosUtil desktop client. The Template Creator (`src-app/pages/templates.astro`) is a separate page in the same bundle, opened only by the developer tool; it is not linked from the main shell. `uiVersion` is derived from the file hashes, so it only changes when the shell changes, not on every site deploy. Bump `apiVersion` in the manifest only for breaking API changes, together with `wosutil.ui.contract.API_VERSION` in the WosUtil repo.
- Shell development: run the WosUtil API with `WOSUTIL_UI_NO_WINDOW=1 WOSUTIL_UI_PORT=8765 WOSUTIL_UI_TOKEN=dev` (PowerShell: `$env:...`), then `pnpm dev:app` and open `http://localhost:4321/?t=dev`. The Vite proxy forwards `/api` (including SSE) to the Python server and edits hot-reload. Set `WOSUTIL_UI_URL=http://localhost:4321/?t=dev` to show that dev URL in the Edge app window instead of a normal browser tab.
- Public deployment is **Cloudflare Pages**: `pnpm deploy:pages` builds with `PUBLIC_REPORTS_API=https://api.wosutil.tech/api`, builds the desktop shell into `dist/ui/` and uploads `dist/` to the `wosutil-site` project. WosUtil downloads the pinned shell from the `wosutil-site.pages.dev` alias (the `wosutil.tech` zone challenges HTML downloads from CI). The API is a Cloudflare Tunnel hostname (`api.wosutil.tech`) backed by the reports stack.
- SEO: per-page title/description, canonical + Open Graph in `BaseLayout.astro`, sitemap, generated `robots.txt`, and `noindex` on the 404 page.

## Commands
- Install: `pnpm install`
- Dev server: `pnpm dev`
- Desktop shell dev server: `pnpm dev:app` (proxies `/api` to `127.0.0.1:8765`; override with `WOSUTIL_API`)
- Typecheck: `pnpm typecheck`
- Tests: `pnpm test` (watch: `pnpm test:watch`)
- Refresh bundled generation presets: `python reports/loopcal/export_site_presets.py` in `wosutil-sim`
- Build: `pnpm build` (output `dist/`; preview: `pnpm preview`)
- Deploy: `pnpm deploy:pages` (Cloudflare Pages direct upload)
- Desktop shell: `pnpm build:app` (output `dist-app/`) and `pnpm package:ui` (output `dist/ui/`)

## Definition of done
`pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm build:app` and `pnpm package:ui` must pass locally, and `dist/` must be sanity-checked (root 302, 404 redirect, all pages render, nav/theme/timer/share work).

## Git workflow
GitHub Flow: `main` is always deployable; all work happens on short-lived branches merged via Pull Requests (squash merge, branch deleted after merge).

### Branch naming
Prefix branches by change type: `feat/` (new functionality), `fix/` (bug fixes), `docs/` (documentation only), `refactor/` (no feature or bug fix), `style/` (formatting or other non-functional changes), `test/` (tests only), `ci/` (CI/CD and build tooling).

### Commit messages
Conventional Commits: `<type>(<scope optional>): <short description in imperative mood>` (first line ≤ 72 chars, no trailing period). Types: `feat`, `fix`, `docs`, `refactor`, `style`, `test`, `chore`, `ci`.
- Write the description in English, imperative mood ("add X", not "added X").
- Keep commits atomic; split unrelated changes (e.g. `fix:` + `style:`).
- Add a body only when the "why" matters; never restate the "how".
- Reference issues in the footer when applicable (`Closes #123`).

### Process
1. Update `main`: `git checkout main && git pull origin main`.
2. Create the branch: `git checkout -b <type>/<short-description>`.
3. Commit in small increments using the conventions above.
4. Push and open a Pull Request (even for solo work: CI plus self-review).
5. Merge via squash, then delete the remote and local branches.

### CI
`ci.yml` runs typecheck, tests and build on every push/PR. Ensure checks pass before pushing; never merge a PR with failing checks.

Keep this file updated when the structure, commands or conventions change.
